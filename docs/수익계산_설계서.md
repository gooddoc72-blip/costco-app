## 1. 목적과 원칙

판매자(사용자)가 **실제로 보낸 주문**에서 얼마가 남았는지를 날짜별로 계산한다.

| 원칙 | 내용 |
|---|---|
| **① 발송건 기준** | 수익계산 대상은 **송장 등록으로 발송처리된 주문 + 코스트코 온라인몰 직배송 주문**뿐이다. 주문만 들어오고 발송하지 않은 건, 앱 밖에서 송장을 넣은 건은 넣지 않는다. (2026-10-26 확정) |
| **② 날짜 = 발송일** | 주문은 **발송한 날짜**의 수익이다. 10/20 주문 → 10/22 발송이면 10/22 수익. 온라인몰 직배송은 영수증 정산에서 표시한 정산일. |
| **③ 구입가 = 판매자가 실제로 낸 돈** | 영수증 정산으로 청구가 확정된 주문은 그 **청구액**이 구입가다. 남의 재고를 빌려 판 건은 **빌린 금액**. |
| **④ 화면과 통계는 같은 저장소** | 홈 달력·월별·대시보드·세무회계는 모두 `profit_settlements`(수익 저장)를 읽는다. 수익계산 화면의 행과 저장 행이 같은 기준이어야 숫자가 맞는다. |
| **⑤ 사람이 고친 값은 지킨다** | 자동 저장은 사람이 고친 행을 덮어쓰지 않는다. 단 날짜는 발송일로 옮긴다. |

## 2. 용어

| 용어 | 뜻 | 저장 위치 |
|---|---|---|
| 발송 기록 | 송장 등록으로 발송처리된 주문. 주문번호·발송일·송장·플랫폼 | `{user}.db dispatch_log` (UNIQUE order_no+발송일) |
| 온라인몰 직배송 | 코스트코 온라인몰에서 사서 코스트코가 고객에게 직접 보낸 주문 | `auth.db online_purchase` (settle_date) |
| 주문 정보 | 판매금액·정산예정금액·고객배송비·수량 | `{user}.db order_history` |
| 청구 품목 | 영수증 정산이 확정한 주문별 물건값(판매자에게 청구한 금액) | `auth.db settle_item` |
| 수익 저장 | 날짜·주문별 수익계산 결과 | `{user}.db profit_settlements` (UNIQUE settlement_date+order_no) |
| 자동 행 | 시스템이 저장한 행 (`match_source='자동'`) | profit_settlements |
| 사람 행 | 화면에서 저장했거나 영수증 정산이 반영한 행 (`수동입력`·`영수증`·`DB-번호` 등) | profit_settlements |

## 3. 대상 선정 규칙

### 3.1 그날의 행
```
그날 행 = { 발송 기록 중 발송일 = 그날 }
        ∪ { 온라인몰 직배송 중 정산일 = 그날, 단 발송 기록이 있는 주문은 제외(중복 방지) }
```
- 둘 다 없으면 **그날 수익계산 대상은 없다.** 예전처럼 결제일 주문이나 옛 데이터(`daily_orders`)로 대신 보여 주지 않는다.
- 저장된 수익 행은 **행을 만들지 않는다.** 위 집합에 있는 주문에 저장값(구입가·택배·박스)만 덮어쓴다.

### 3.2 제외되는 주문
| 경우 | 처리 |
|---|---|
| 주문만 있고 발송 안 됨(결제완료·상품준비중) | 제외 |
| 취소·반품 | 제외 (발송 후 취소면 발송 기록은 남지만 정산 금액 0) |
| 앱 밖에서 송장 입력(스토어 관리자 화면 직접) | 발송 기록이 없어 제외. 넣으려면 영수증 정산의 **'네이버 발송정보 반영'**으로 발송 기록을 먼저 만든다 |
| 택배 휴무일(주말·공휴일) | 그날 발송이 없으면 대상 없음. 휴무일 주문은 다음 영업일 발송일로 잡힌다 |

### 3.3 날짜가 여러 개인 주문
| 경우 | 수익 날짜 |
|---|---|
| 분할 발송(한 주문 여러 날) | **첫 발송일**(`MIN(dispatched_at)`) |
| 재발송(반품 후 재배송, 송장 다름) | 첫 발송일. 두 번째 발송은 택배비 청구에만 영향 |
| 온라인몰 + 발송 기록 둘 다 | 발송일 |

## 4. 계산식

```
수입 = (정산예정금액 + 실정산배송비) − (구입가격 + 택배원가 + 박스원가)
```

### 4.1 항목 정의

| 항목 | 정의 | 출처·우선순위 |
|---|---|---|
| **정산예정금액** | 판매금액에서 플랫폼 수수료를 뺀, 우리가 받을 돈 | ① (화면) 실정산 확정액 — 정산 매칭(`settlement_matches`)·쿠팡 정산금(`coupang_settlements`)이 있으면 ✅ 표시와 함께 대체 ② `order_history.settlement` ③ `dispatch_log.expected_settlement` |
| **실정산배송비** | 고객이 낸 배송비 중 정산받는 몫 | `배송비 합계 × 1.0` (네이버 수수료는 판매가에만 붙어 정산예정금액에 이미 반영) |
| **구입가격** | 그 주문 물건을 사는 데 든 돈 | 4.2 참고 |
| **택배원가** | 택배 1건 비용 | ① 행별 저장값 ② 사용자 설정 `shipping_cost` (없으면 2,000, 10만 초과 이상치는 1,800) |
| **박스원가** | 포장재 비용 | ① 행별 저장값 ② (화면) 관리자 포장 배정 `order_packaging` ③ 사용자 설정 `box_cost` (없으면 300, 1만 초과 이상치는 300) |

### 4.2 구입가격 우선순위 (`compute.compute_row`)

| 순위 | 근거 | 출처 표시 | 계산 |
|---|---|---|---|
| **0** | **영수증 정산 청구액** | `정산청구` | `settle_item` 그 주문 금액 합계(0원 제외). 분할 청구는 더한다. **빌린 재고는 빌린 금액**(할인 재고 +1,000원, 정상가 재고는 산 값) |
| 1 | 화면에서 고른 키워드(수동) | `수동입력` | 그 제품 단가 ÷ 소분수 × 수량 × 묶음배수 |
| 2 | 상품번호 매칭 → 최근 90일 영수증에 그 번호가 있으면 | `영수증` | 영수증 실단가 ÷ 소분수 × 수량 × 묶음배수 |
| 2' | 상품번호 매칭 → 영수증 없으면 | `DB-번호` | 제품 DB 단가 ÷ 소분수 × 수량 × 묶음배수 |
| 3 | 영수증 상품명 매칭 | `영수증` | 영수증 단가 ÷ 소분수(이름의 'x N개') × 수량 |
| 4 | 키워드 토큰 매칭 | `DB-키워드` | 제품 DB 단가 기준 |
| 5 | 저장된 구입가 | `DB-키워드` | 저장값 |
| – | 없음 | `미매칭` | 0 → 통계에서 수익 0으로 처리 |

- **소분수(split_qty)**: 코스트코 한 묶음을 N개로 나눠 팔면 단가 ÷ N.
- **묶음배수(sell_factor)**: 상품명 'x N개'처럼 한 주문에 묶음 N개면 × N.
- **타인재고 웃돈**: 순위 1~5로 계산된 행 중 남의 재고에서 나간 행은 웃돈(`inventory_moves.surcharge`)을 더하고 출처에 `+타인재고`를 붙인다. **순위 0(정산청구)에는 더하지 않는다** — 청구액에 이미 들어 있다.
- **저장값보다 청구액 우선**: 정산청구 행은 옛 저장 구입가로 덮지 않는다(화면 복원·자동 저장·API 공통).
- **본인 결제된 재고(청구 0원)**: 순위 0에서 빠지고 순위 1~5로 계산한다(재고 구입가가 원가).

### 4.3 판매 단위
- 수량은 고객 주문 수량. 재고 차감·영수증 매칭은 `수량 × 묶음배수` 소분 단위로 한다.

## 5. 저장 설계 (`profit_settlements`)

### 5.1 스키마 요지
| 컬럼 | 뜻 |
|---|---|
| settlement_date | 수익 날짜(= 발송일 / 온라인몰 정산일) |
| order_no | 상품주문번호 — `UNIQUE(settlement_date, order_no)` |
| order_amount · settlement_amount · shipping_fee · extra_shipping | 판매금액·정산예정금액·고객배송비·제주/도서 추가배송비 |
| cost_price · delivery_cost · box_cost | 구입가·택배원가·박스원가 |
| match_source · matched_keyword · matched_product_no | 구입가 출처(4.2)·매칭 정보 — `자동`이면 자동 행 |
| split_qty · sell_factor | 소분·묶음 |

### 5.2 저장하는 때 (트리거)
| 때 | 함수 | 범위 |
|---|---|---|
| **발송 기록이 저장되는 순간** (송장 화면 발송처리, 관리자 발송 파일, 스토어 대신 발송, 네이버 발송정보 반영) | `db_dispatch_log.log_dispatch_success` → `save_dispatch_profit(사용자, 발송일)` | 그날 |
| **온라인몰 직배송 표시** | `db_online_purchase.mark` → `save_dispatch_profit` | 그 정산일 |
| 주문 자동 수집 작업(12시 등) | `auto_task.save_recent_dispatch_profit(days=3)` | 최근 3일 발송일 |
| 화면 💾 정산 데이터 저장 · 📊 정산저장 | `save.py` → 저장 후 `clean_stale_auto` | 그날 |
| 영수증 정산 확정 | `receipt_settle.apply_receipt_settlement` | 그 주문 행의 구입가를 청구액으로 갱신 |

### 5.3 `save_dispatch_profit(사용자, 날짜)` 규칙
1. 그날 대상(3.1)을 다시 계산한다. 저장값은 무시하고 지금 매칭·설정·청구액으로 계산한다.
2. **이 날짜의 대상이 아닌 행 정리**(`enforce_dispatch_basis`) — 출처와 상관없이:
   - 다른 날 발송(또는 온라인몰 정산)된 주문 → **그 날짜로 옮긴다**. 그 날짜에 이미 행이 있으면 여기 것을 지운다.
   - 발송 기록도 온라인몰 표시도 없는 주문 → **지운다**.
3. **이 날짜 대상 주문이 다른 날짜에 저장돼 있으면**: 자동 행은 지우고 여기 새로 저장한다. 사람 행은 **이 날짜로 옮겨** 값을 유지한다.
4. 이 날짜에 사람 행이 있는 주문은 덮어쓰지 않는다. 나머지는 `자동`으로 저장한다(구입가 0도 저장 — 월별 점검이 '구입가 없음'으로 짚는다).

### 5.4 기존 데이터 정리 도구
`fix_profit_dispatch_basis.py` — 기간(기본 10/1~오늘)의 모든 발송일·온라인몰 정산일·저장 날짜에 `save_dispatch_profit`을 두 번 돌린다.
```
미리보기: python fix_profit_dispatch_basis.py <복사본 경로> [--from 2026-10-01]
적용:     python fix_profit_dispatch_basis.py /opt/costco-app --apply   # data/backup_profit2_시각/ 에 백업
```
10/26 미리보기(운영 복사본): 기준 어긋남·누락 777 → 11건, 10월 행 702 → 1,002, 수익 289만 → 450만원.

## 7. 화면 기능 정의 (Streamlit › 운영 › 수익 계산)

### 7.1 일별 계산
| 요소 | 기능 |
|---|---|
| 날짜 선택 · 📋 조회 | 그날 대상(발송+온라인몰)을 불러온다. 위에 출처 한 줄: "🚀 발송 N건 (송장 기준) + 🛒 온라인몰 직배송 M건 — 정산저장 K건 반영" / 대상 없으면 안내 |
| 택배비·박스비 입력 | 그날 기본값(행별 값이 없을 때) |
| 📊 일별 정산표 | 행마다: 수취인·상품·수량·정산예정금액(✅ 실정산)·배송비·구입가격(출처 배지: 정산청구·영수증·DB·수동·+타인재고·소분÷N)·택배원가·박스원가·수입. 행별 구입가·택배·박스·키워드 수정 |
| 📊 정산저장 (행 체크 후) | 체크한 행을 수익 저장(사람 행) → 그날 대상 밖 행 정리. 제품 DB는 바꾸지 않는다 |
| ❌ 매칭 해제 | 그 행의 수동 키워드·영수증 선택을 지운다 |
| 💾 제품가격 DB 저장 | 고친 단가를 제품 DB에 반영 + 수익 저장 |
| 💾 정산 데이터 저장 | 그날 행을 수익 저장(사람 행) → 대상 밖 행 정리 |
| 🗑 이 날짜 정리 | (두 번 눌러 확인) 그날 옛 주문 데이터 정리 |
| 📋 합계 | 정산예정 + 실정산배송비 − 구입가 − 택배 − 박스 |
| 🔴 수익 마이너스 판매가 검토 | 마진이 마이너스인 상품의 네이버 판매가 조정 제안·적용 |
| 영수증 등록(내장) | 영수증 단가를 제품 DB에 반영 |

### 7.2 월별 분석·점검
| 요소 | 기능 |
|---|---|
| 📊 월 합계 | 매출·정산·구입가·수익 |
| 📆 일별 내역 · 🏷 상품별 수익 | 날짜별·상품별 |
| 🔍 점검·수정 | 중복·구입가 없음·금액 이상 행을 골라 수정(💾 수정 저장) · 🗑 중복 지우기 |

## 9. 알려진 한계 · 다음 과제

| 한계 | 영향 | 방향 |
|---|---|---|
| **자동 저장은 실정산 확정액·포장 배정 박스비를 반영하지 않는다**(화면만 반영) | 화면과 홈 달력·월 합계가 실정산/포장 차이만큼 다를 수 있다 | `compute_dispatch_rows`로 실정산·포장 배정을 옮겨 화면·자동 저장 공통화 |
| 앱 밖에서 보낸 주문은 빠진다 | 그 매출·수익이 통계에 없다 | 매일 '네이버 발송정보 반영'을 자동으로 돌리는 작업 검토 |
| 분할 발송은 첫 발송일에 전액 | 두 번째 발송일 수익은 0 | 현재 규칙 유지(청구는 분할 반영) |
| 정산 확정 직후 수익 행이 바로 다시 계산되지 않는다(구입가만 갱신) | 택배·박스 등은 다음 저장 때 반영 | `finalize` 뒤 해당 발송일 `save_dispatch_profit` 호출 검토 |
| 자동 테스트 없음 | 규칙 변경 시 회귀 위험 | `compute_row`·`enforce_dispatch_basis` 단위 테스트 |
