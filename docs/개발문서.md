### 4.3 서버 복사본에서 검증하기 (실제 사용 중인 방식)
운영 DB를 건드리지 않고 시험할 때는 다음 순서로 한다.
1. 코드를 tar로 묶어 서버 `/tmp/pf`에 푼다.
2. DB는 sqlite `.backup`으로 복사한다(원본은 읽기 전용).
3. Streamlit은 `AppTest`, FastAPI는 `TestClient` + `app.dependency_overrides[require_admin]`로 돌린다.
4. TypeScript는 서버 `node_modules`를 심볼릭 링크(`/tmp/mb`)해서 `tsc --noEmit`을 돌린다.

> 운영 DB를 고치는 스크립트(`--apply`)는 미리보기(dry-run) 결과를 확인한 뒤 **관리자가 직접 실행**한다. 실행 전에 `*.bak.*.db` 백업을 만든다.

## 5. 코드 구조와 규칙

### 5.1 계층
```
화면      app.py + pages_lib/*.py (Streamlit)   mobile/src/app/* (Next.js)
           │                                    │ lib/client/*.ts
           │                                    ├─ /m/api/* (Next 라우트, SQLite 직접)
           │                                    └─ /api/*   (FastAPI)
API       api/main.py, api/billing.py, api/receipt_settle.py, api/trends.py, api/auto_settle.py
서비스    receipt_settle.py, receipt_settle_service.py, settle_core.py, dispatch_upload.py,
          services.py, pages_lib/profit_calc/{loader,compute,enrich}.py, trend_research.py …
DB 접근   db.py(re-export) → db_core.py, db_auth.py, db_products.py, db_settle.py, db_deposit.py …
저장소    data/auth.db · data/admin.db · data/{username}.db
```
**원칙:** 계산은 서비스 함수(순수 함수에 가깝게)에 두고 Streamlit과 FastAPI가 **같은 함수**를 부른다. 예: 수익계산 `pages_lib/profit_calc/`, 영수증 정산 `receipt_settle_service.py`.

### 5.2 DB 접근 (`db_core.py`)
- `get_auth_db(timeout=30, row=False)` — auth.db, **WAL**, busy_timeout 30초, synchronous=NORMAL. Streamlit·FastAPI·크론이 동시에 쓰기 때문이다.
- `retry_on_lock(fn, attempts=4, base_delay=0.4)` — 잠금 충돌 재시도.
- `get_user_db(username)` — `data/{username}.db`, 없으면 만든다.
- 호출하는 쪽은 `from db import ...` (하위호환 re-export 레이어).
- 새 테이블은 사용하는 모듈 안에서 `CREATE TABLE IF NOT EXISTS`로 만든다(별도 마이그레이션 도구 없음). 큰 구조 변경은 `migrate_*.py`로 하고 `--dry-run`/`--verify`를 지원한다.

### 5.3 설정값
| 범위 | 함수 | 저장 위치 |
|---|---|---|
| 전역(관리자) | `get_global_setting(key)` / `set_global_setting(key, v)` (db_auth) | `auth.db app_settings` |
| 사용자별 | `get_setting(user, key)` / `set_setting(...)` / `get_all_settings(user)` (db_products) | `{user}.db settings` |

### 5.4 AI 호출 (`ai_service.py`)
- `get_ai_keys()` → (anthropic_key, gemini_key). 전역 설정 → 사용자 설정 → 전체 사용자 순으로 찾는다(20초 캐시). 관리자 전역 키를 모든 사용자가 공유한다.
- `ai_complete(system, user_msg, ..., feature='')` — **Gemini 먼저, 실패하면 Claude**. 반환은 (text, error, provider).
- 모델: 기본 `claude-haiku-4-5-20251001`, 비전 `claude-sonnet-5` (HTTP 직접 호출, 공식 SDK 미사용).
- 사용량은 `set_current_user()`로 사용자에게 귀속돼 `db_ai_usage`(auth.db `ai_usage_log`)에 쌓이고, 월 한도를 검사한다.

### 5.5 성능 도구
- `run_memo.py` — 한 화면을 그리는 동안만 쓰는 스레드별 캐시. `begin()`·`end()` 사이에서만 동작하므로 API·크론에는 영향이 없다. `@memo`는 db_products, db_dispatch_log, receipt_settle 등에 붙어 있다. **쓰기 후에는 `run_memo.clear()`.**
- Streamlit 캐시 헬퍼(TTL 30~180초) + `invalidate_data_cache()`.
- 공유 제품 DB는 파일 수정시각을 서명으로 쓰는 캐시가 있다(`get_shared_products`).

### 5.6 백그라운드 작업
- `auto_task.py --task N --user U` — 작업 1~9(장보기 카톡, CJ 접수+발송, 크롤링, 순위, 주문 수집, 등록상품 수집, 자동 등록, 재고 동기화). 맨 처음에 `task_gate.gate_from_argv()`로 슬롯을 잡는다.
- 로그: `data/auto_task.log`(5MB×3), `data/user_logs/`, `data/task_queue.log`, 서비스 로그는 `journalctl -u costco-app` / `-u costco-api`.
- 카페24 동기화는 매시간 크론 + DB 간격 게이트(enabled / interval_hours / last_run).
- 관리자 PC의 `tools/daily_settle.py`가 매일 18:00에 CJ 파일과 영수증을 `/api/admin/auto/*`로 올린다(`tools/cj_lois.py`가 Playwright로 CJ 엑셀을 내려받음).

### 5.7 크롬 확장 (`chrome_extension/`)
- Manifest V3, “코코비즈 순위추적” **v0.20.1**. 권한: tabs, scripting, storage, alarms, cookies.
- 사용자 브라우저에서 네이버 쇼핑 순위를 최대 20페이지(800위)까지 재고 결과를 cocobiz로 보낸다. 서버 IP 한 개로는 2페이지 이후 차단됐기 때문이다(2026-09-26).
- 중지 버튼이 있다(`STATE.stopRequested`). 패널은 2초마다 상태를 확인한다.
- 설치: `chrome://extensions` → 압축해제된 확장 프로그램 로드. AI 토큰 비용은 들지 않는다.

### 5.8 라이선스 (설치판)
- `COSTCO_LOCAL=1`일 때만 `license_client.py`가 동작한다. Windows MachineGuid로 PC를 식별하고, `/license/verify`에서 키 1개당 PC 1대로 묶는다. 키 형식은 `COCO-XXXX-XXXX-XXXX`이고 관리자 화면에서 발급·해제한다.

## 6. API 레퍼런스

### 6.1 인증 (공통)
- 세션 테이블 `auth.db sessions(token, username, created_at, expires_at)`을 Streamlit·FastAPI·Next가 **함께 쓴다.**
- 토큰 찾는 순서(FastAPI `_extract_token`): `Authorization: Bearer` → 쿠키 `sid` → `?sid=`
- `require_user` → 없으면 401. `require_admin` → 관리자가 아니면 403. (`api/billing.py`에 같은 로직의 독립 버전이 있고 다른 라우터가 이것을 가져다 쓴다.)

## 7. 개발 규칙

1. **수정 범위 격리** — 요청받은 부분만 고친다. Edit로 최소 범위만 바꾼다.
2. **돈 계산은 원장이 정본** — 청구액은 `settle_item` 합계에서만 만든다(`recompute_invoice`). 예치금 잔액은 `deposit_ledger` 합계로만 계산한다. 잔액·합계를 따로 저장하지 않는다.
3. **되돌릴 때는 지우지 말고 상쇄 행** — `spend_void` + `refund`처럼 남긴다.
4. **입금완료(`paid`) 청구서는 금액을 건드리지 않는다.**
5. **자동으로 남의 재고를 차감하지 않는다** — 영수증에 없는 출고는 관리자가 출처를 확인한다.
6. **사용자 선택은 DB 초안에 저장** — 재시작에도 살아야 한다(`settle_draft`, `settle_work`).
7. **커밋은 내 변경만** — 다른 사람이 작업 중인 파일은 섞지 않는다(필요하면 `git add -p`).
8. 커밋 메시지는 한국어로 “영역: 무엇을 왜”. 큰 작업은 `DEV_LOG.md`에 날짜별 “## YYYY-MM-DD 업데이트”로 남긴다. 세션 로그는 `docs/세션로그_YYYY-MM-DD.md`(커밋 표 → 완료 작업 → 다음에 할 것).
9. `import re`는 루프 밖에서 한 번만.
