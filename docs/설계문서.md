> 함께 보는 문서: [개발문서](개발문서.md) · [UI문서](UI문서.md) · 정산·예치금 상세 규칙은 루트 `CLAUDE.md`

## 1. 시스템 개요

### 1.1 무엇을 하는 프로그램인가
코스트코 **구매대행 사업자 여러 명(사용자)**이 네이버 스마트스토어·쿠팡·카페24에서 받은 주문을, **관리자**가 코스트코 매장에서 한꺼번에 사서 택배로 보내고, 사용자별로 물건값을 정산·청구하는 일을 자동화한다.

| 역할 | 하는 일 |
|---|---|
| **사용자(판매자)** | 자기 스토어에 코스트코 상품 등록, 주문 수집, 장보기 목록 제출, 송장 등록, 수익 확인, 청구액 입금(또는 예치금) |
| **관리자(운영자)** | 매장 구매, 영수증 등록, 택배 발송, 영수증↔발송 매칭, 정산·청구·입금 확인, 재고·반품 관리, 회원·공유 DB 관리 |
| **직접구매 계정** | 자기가 직접 매장에서 사는 사용자. 매칭·재고 정리는 하지만 청구 대상은 아니다 |

### 1.2 하루 업무 흐름
```
 ① 주문 수집 (12시 마감)        네이버·쿠팡·카페24 API → order_history / daily_orders
        │
 ② 장보기 목록                  사용자별 목록 → 관리자 합본 → 카톡 전송
        │
 ③ 매장 구매                    관리자가 코스트코에서 구매 (영수증 발생)
        │
 ④ 택배 발송 (17시 마감)        CJ 접수 → 배송상세 엑셀 업로드 → 사용자별 분류 → 네이버·쿠팡 발송처리
        │                       → dispatch_log 기록 + 재고 차감
 ⑤ 영수증 등록                  PDF/사진(AI 판독) → receipt_items
        │
 ⑥ 영수증 정산(매칭)            발송건 ↔ 영수증 품목 매칭 → 초안(settle_draft) → 관리자 확인
        │
 ⑦ 정산 확정                    settle_item(청구 근거) → settle_invoice(청구서)
        │                       → 주문 원가·수익계산 반영 → 재고 출고·보유자 적립
 ⑧ 청구·입금                    청구 → 계좌 입금 확인 또는 예치금 차감 → 미입금자 관리
        │
 ⑨ 수익 확인 · 네이버 정산 대조  수익계산(일·월), 네이버/쿠팡 정산금 역추적 매칭
```
택배비·포장비는 물건값 청구서에 섞지 않고 **따로 청구**한다.

### 1.3 범위 밖 / 보조 기능
상품 등록(네이버·카페24 대행), 순위 추적(크롬 확장), 세무회계·통장 거래, SNS 트렌드 조사, 마진계산기, 라이선스(PC 설치판).

### 2.2 설계 원칙
1. **돈은 원장 하나에서만 나온다.** 청구액은 `settle_item` 합계, 예치금 잔액은 `deposit_ledger` 합계. 합계를 따로 저장하지 않으므로 화면마다 금액이 달라질 수 없다. (예전에 청구 금액 저장소가 넷이어서 화면마다 금액이 달랐다.)
2. **되돌리기는 지우지 않고 상쇄한다.** 차감 취소는 `spend_void` + `refund` 두 줄로 남긴다.
3. **입금완료(`paid`)된 청구서는 금액을 바꾸지 않는다.**
4. **자동화는 초안까지, 확정은 사람이.** 무인 매칭은 초안만 만들고, 정산 확정·예치금 차감·잔량 재고 입고·남의 재고 사용은 관리자가 확인한다.
5. **같은 계산은 한 함수.** Streamlit·FastAPI·크론이 같은 서비스 함수를 부른다.
6. **사용자 선택은 DB에 저장한다.** Streamlit 세션은 재시작하면 사라지기 때문이다.
7. **사용자 데이터 분리.** 사용자별 DB 파일을 두고, 여러 사용자가 함께 보는 데이터(정산·재고·영수증·예치금)만 `auth.db`에 둔다.

### 2.3 기술 선택과 전환 방향
- **현재:** Streamlit이 화면과 로직을 함께 가진다. 화면 전체를 다시 그리는 방식이라 **느리고**, 재시작하면 입력이 리셋되며, 화면 오류가 잦다.
- **목표:** 화면은 Next.js(`/m`), 업무 로직은 파이썬 서비스 + FastAPI. Streamlit에는 응급 수정만 한다.
- **진행:** 정산·청구(`/billing`), 영수증 정산 1차(`/receipt-settle`), 트렌드(`/trends`)를 이전했다. 이전 현황은 UI문서 5장 참고.
- **원칙:** Next.js 자체 API(`/m/api`)는 기존 단순 화면용으로만 두고, 새 기능은 FastAPI로 만든다. 계산 로직을 TypeScript로 다시 쓰지 않는다.

## 5. 핵심 업무 설계

### 5.1 주문 수집
- `auto_task --task orders`(작업 5) 또는 화면 버튼으로 실행한다.
- 순서:
  1. 네이버 `get_new_orders`(변경시각 기준 API, 429·403 재시도)와 쿠팡 `get_orders`로 주문을 가져온다.
  2. `split_orders_by_cutoff`로 나눈다. 사용자별 마감시각 `order_cutoff_hour`의 기본값은 12시다.
  3. `save_order_history`, `save_daily_orders`로 저장한다.
  4. 최근 3일 발송 수익을 자동 저장한다.
  5. 네이버 정산 10일분을 역추적 매칭한다.
  6. 카카오로 알린다.

### 5.2 상품 매칭 우선순위
**수익계산**(`services.match_product_to_db`):
1. 수동 키워드 오버라이드
2. `naver_origin_pno`
3. 코스트코 번호
4. 키워드 토큰
5. 저장된 원가

**영수증 매칭에서 코스트코 번호를 고르는 순서**:
1. 사용자 상품 DB의 번호(`user_product_costco_no`)
2. 공유 맵
3. 상품명 유사도

**소분:** `split_qty`가 N이면 코스트코 한 묶음을 N개로 나눠 판다. 원가는 `(단가 ÷ split_qty) × 수량 × sell_factor`이고, `sell_factor`는 상품명의 “x N개”에서 뽑는다.

### 5.3 발송
여러 경로가 있어도 끝은 모두 `log_dispatch_success`로 같다. 이 함수는 주문번호 기준으로 한 번만 기록하고 재고를 차감한다.

| 경로 | 설명 |
|---|---|
| 관리자 CJ 엑셀 업로드 (주 경로, 17시 마감) | `dispatch_upload`가 주문번호로 주문 주인을 찾아 사용자별로 분류한다. 업체코드를 학습하고 외부 건은 제외한다. 관리자가 사용자를 골라 **그 사용자의 API 키로** 네이버·쿠팡 발송처리를 한다(`ship_for_user`). |
| 사용자 송장 화면 | 사용자 본인이 발송처리 |
| 무인 | `tools/daily_settle.py` → `/api/admin/auto/dispatch` |
| 앱 밖에서 발송한 건 | `dispatch_sync.pull_naver_dispatch` / 수동 표시 |

**합배송:** 같은 받는 사람·주소의 네이버 주문 여러 건에 같은 송장을 보낸다(`combined_siblings`, `expand_combined`).

**주문번호 없는 CJ 행:** “신선식품(냉장)”처럼 주문번호가 없는 행은 받는 사람으로 최근 30일 주문에서 유일하게 맞는 건을 찾아 연결한다(`relink_no_orders`).

### 5.4 영수증 정산 (매칭)
`receipt_settle_service.run_match(d)`는 Streamlit과 Next가 같은 파이프라인을 쓴다.
1. 주문번호 없는 발송건을 다시 연결한다.
2. **재고 풀**을 만든다: 영수증 수량 × split − 이미 정산된 수량.
3. 이미 정산된 주문과 분할 발송 수량을 뺀다.
4. `allocate_dispatched_to_receipt`로 발송건마다 영수증 품목을 붙인다. 시도하는 순서:
   1. 그날 발송 때 본인 재고에서 나간 것은 재고 행으로 둔다.
   2. 판매자 본인의 보유 재고를 먼저 쓴다.
   3. 장보기 목록 연결.
   4. 상품 DB 번호.
   5. 상품명 유사도.
5. 관리자 초안(`settle_draft`)을 덮어 적용한다. 수동 선택이 우선한다.
6. 온라인몰 직배송 행을 만든다.
7. AI 보조 매칭을 한다.
8. 마지막 수단으로 재고 이월을 한다.
9. 이전 날짜 미정산분을 이월한다. 번호가 정확히 같은 것만 하고, 화면에는 선택 시에만 보인다.

**관리자 확인이 필요한 경우**:
- **영수증 수량보다 많이 나간 건(초과분):** 배치 상세에 표시하고, 처리를 ✅ 영수증가 청구 / 📦 재고 출고 / ✂️ 끊기 중에서 고른다.
- **영수증에 없는 출고(미분류):** 누구의 재고에서 나갔는지 관리자가 지정한다. 자동 추천과 자동 금액을 제안한다.
- **남은 물건(잔량):** 최대 소분 단위로 맞춰 계산한다. 재고·온라인 건은 제외한다. 보유자는 그날 장보기 요청자로 추천하고, 관리자가 체크한 것만 재고로 입고한다.

### 5.5 정산 확정
`settle_core.finalize(d, rows)`:
1. 행을 출처별로 원장 행으로 바꾼다(receipt / stock / manual / direct / online / self). **0원 행은 넣지 않는다.**
2. 주문 원가(`order_history.cost_price`)와 `profit_settlements`에 반영한다. 다른 날 이미 정산된 금액도 더한다.
3. 확정된 매칭에서 코스트코 번호를 학습한다(`learn_costco_mappings`).
4. `save_settlement`로 원장에 쓴다.
   - **추가(merge)**가 기본이다. 이번 회차에 매칭된 주문만 갱신하므로, 영수증을 나눠 올리는 날 오전분이 사라지지 않는다.
   - **교체(replace)**는 선택할 수 있다.
   - 쓴 뒤 `recompute_invoice`로 청구서를 다시 계산한다.
5. 재고 출고 행만큼 재고를 차감한다(`consume_for_sale(owner=…)`).
6. **교차 재고 적립:** 남의 재고를 쓴 경우 재고 주인에게 `stock_credit`으로 예치금을 적립하고, 해당 이동을 `SETTLED`로 바꾼다. 주문번호 메모로 중복 적립을 막는다.
7. **정산 취소** 시:
   1. 적립을 취소한다(`stock_credit_cancel_orders`).
   2. `SETTLED` 이동을 다시 연다.
   3. 입금완료분은 남긴다.

### 5.6 청구 · 입금 · 예치금
- 청구서 상태: `draft` → `billed` → `paid`. **미입금자는 `billed`만 해당한다.**
- 청구액은 물건값(`settle_item` 합계)뿐이다. 택배·포장비는 별도로 청구한다(`ship_fee`, `pack_fee`는 0).
- 예치금 차감은 입금 방법의 하나다. `mark_billed` → `deduct` → `mark_paid('예치금 차감')` 순서로 처리하고, 되돌릴 때는 `unmark_paid` + `undo_deduct`를 함께 부른다.
- 차감은 버튼으로 하루 한 번만 한다(부분 UNIQUE). 잔액이 모자라도 막지 않고 마이너스로 두며, “추가 예치 필요”를 표시한다.
- `deposit_ledger.kind` 종류:

| kind | 뜻 | 부호 |
|---|---|---|
| `charge` | 예치 입금 | + |
| `spend` / `spend_void` | 그날 구매 차감 / 되돌린 차감 | − |
| `refund` | 차감 되돌림 | + |
| `adjust` | 관리자 수동 조정(사유 필수) | ± |
| `return_credit` | 매장 반품 환불 적립 | + |
| `stock_credit` | **재고 판매 적립** — 내 재고를 다른 판매자가 썼을 때 | + |

- 직접구매 계정: 매칭 대상(`matchable_users`)이지만 청구 대상(`billable_users`)은 아니다. 대리구매(proxy=1)만 택배비를 청구한다.

### 5.7 재고 규칙 (2026-10-22 개정)
- **단위:** 소분 단위. 로트의 `qty_in`은 묶음 수 × split_qty다.
- **차감:** `consume_for_sale`은 **판매자 본인 로트만**, 오래된 것부터 쓴다. 남의 재고를 **자동으로 차감하지 않는다.** 다른 사람 재고는 관리자가 영수증 정산에서 주인을 지정했을 때만 쓴다.
- **금액:**

| 경우 | 청구 금액 |
|---|---|
| 본인 재고 출고 | 아직 청구 안 된(미납) 분량 금액. 이미 낸 재고는 다시 청구하지 않는다(`own_unpaid_units`, `paid`) |
| 타인 재고, 할인가로 산 재고(`list_price > unit_cost`) | 할인가 + **1,000원** |
| 타인 재고, 정상가로 산 재고 | 구입가 |

- **재고 주인 적립:** 타인 재고 판매액은 확정할 때 주인 예치금으로 적립된다.
- **재고 넘기기:** 정산 장부 탭에서 사용자 사이에 재고를 옮긴다.
- **반품 알림:** 30일 반품 기한 알림(`get_return_due_lots(30)`).
- **수동 입고:** 재고 관리 › ➕ 수동 입고.

### 5.8 수익계산
```
수입 = (정산예정금액 + 실정산배송비) − (구입가격 + 택배원가 + 박스원가)
실정산배송비 = 배송비합계 × (1 − naver_ship_fee_commission_rate%)
구입가격 = (unit_price ÷ split_qty) × 수량 × sell_factor
```
- 데이터 우선순위: `profit_settlements` → `dispatch_log` → `order_history` → `daily_orders`.
- 발송일 기준으로 자동 저장한다. 다른 날 발송된 주문의 낡은 자동 행은 발송일로 옮기고 정리한다(`clean_stale_auto`).
- 수익이 마이너스인 상품은 네이버 판매가 재검토 목록에 올린다.

## 8. 보안 · 권한
- 비밀번호는 bcrypt로 저장한다(옛 sha256 계정도 로그인은 가능하다).
- 세션 토큰은 `secrets.token_urlsafe(32)`로 만들고 30일 동안 유효하다.
- 관리자 API는 서버에서 `require_admin`(403)으로 막는다. Next 화면에는 아직 페이지 단위 관리자 검사가 없다(개선 대상).
- 사용자 API 키는 각 사용자 DB의 `settings`에, 공용 키는 `app_settings`에 둔다.
- 회원 삭제(`db_user_cleanup`)는 예치금 잔액이 0이 아니거나 미입금 청구서가 있으면 막는다.
- 운영 DB를 바꾸는 일괄 스크립트는 미리보기 → 백업 → 관리자 실행 순서로 한다.
